# AMEX local decision v1

This module lives only in `ymlulu/nextbonus-assessment-test`. It does not modify Discover or the production Web catalog.

## Evaluation boundary

The standalone questionnaire's versioned facade now optionally returns `evaluation`, separate from its `questionnaire` schema. The Amex-specific pure engine `engines/amex-decision-v1.js` reads client-held answers in memory and returns two independent signals:

- `application.status`: `MODEL_ONLY`, `ELEVATED_RISK` or `INSUFFICIENT_DATA`; `application.base_risk` follows the existing, locally bundled A1–A4 Assessment credit profile matrix and Amex sensitivity. It does **not** predict a numerical approval probability.
- `bonus.status`: `NO_TRIGGER_FOUND`, `LIKELY_RESTRICTED`, or `NEEDS_REVIEW`; this is an ordinary-public-offer **assumption** or a special explicit `NLL`/rule-override scenario, not a verified live offer or guaranteed bonus.

Each applied source rule produces a distinct `rule_results[]` record with a dimension, status (`CLEAR`, `TRIGGERED`, `MISSING`, `REVIEW`), an ID, and a brief reason. The 31-source-row AMEX inventory is preserved. Exactly **23** are executable rule definitions; eight meta/reference/inactive rules do not become blockers. This is **limited deterministic evaluation of matching facts**, not a wholesale promotion of the full source workbook into certified issuer underwriting rules.

## Required structured facts

`F02_ISSUER_APPLICATION_HISTORY` is now a structured object rather than unparseable free text:

```js
{
 approved_revolving_90d: 0,                  // integer 0 or greater
 approved_revolving_5d: 'NO',                // YES | NO
 same_product_applied_or_approved_90d: 'NO'  // YES | NO
}
```

The form only asks fields that apply to the selected product. Amex charge cards do not acquire revolving-specific 1/5 or 2/90 questions. Partially completed structured facts are **not** treated as fully answered.

`F10_ISSUER_PORTFOLIO_COUNT` is the count for the applicable revolving / charge card type. `F03_CARD_HISTORY` is an explicit multi-selection of ever-held cards, not welcome-bonus receipts; `F07_MARRIOTT_HISTORY` is Marriott/Ritz-Carlton family history and does not establish time windows by itself; `F08_RELATIONSHIP` is an eligible account flag. Baseline `a1`…`a4` continue to use the established, reviewed generic credit model.

The UI never posts, saves or uploads answers. The results stay in browser memory, not even localStorage. Results are generated by on-device JS from static versioned data.

## Conservative interpretations

- Amex credit-card 1/5 and 2/90 spacing and same-product 90-day timing raise application risk; a triggered risk **does not certify rejection**.
- The five-revolving-card and ten-charge-card counts are issuer-related risk signals, **not absolute hard caps**.
- Standard assumed Lifetime/Family Language with positive, exact prior holding history yields `LIKELY_RESTRICTED`; NLL removes only same-product Lifetime by default. Family clauses must be overridden individually when a verified special offer lacks them.
- Personal Delta family is never copied into Delta Business. Hilton different personal tiers do not establish a cross-tier bonus block.
- Marriott cross-issuer and old-version history requires exact former product and application/bonus dates; nonempty records return `NEEDS_REVIEW` instead of an invented 30/90/24 decision.
- For profiles with no known history, `NO_TRIGGER_FOUND` means *no source-trigger found under selected offer assumptions*, **not** official welcome bonus eligibility. The actual pop-up application warning and offer terms govern.
- A missing fact or target-eligibility condition returns an explicit `MISSING` or `REVIEW`, not an implicit `CLEAR`.

**Not included:** HP-specific standalone scoring, numerical approval odds, official real-time offer parsing, issuer underwriting verification, certified Marriott matrix execution, full cross-issuer rule evaluation, remote POST evaluation, and integration into Discover.
